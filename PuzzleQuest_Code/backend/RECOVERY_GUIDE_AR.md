# PuzzleQuest — النسخ الاحتياطي والاسترجاع الآمن

## حقائق مهمة
- ينشئ النظام نسخة `.pqb` مشفّرة بصيغة PQB1 باستخدام `sodium` ومفتاح مشتق من `APP_KEY` الحي.
- النسخة تحتوي جداول قاعدة البيانات (schema + JSONL)، ملفات Laravel الخاصة في `puzzlequest_app`، وملفات الويب في `public_html/puzzlequest.50sols.com`، وأصول المراحل ومجلد `storage/app` بما فيه بيانات اللاعبين وملفات الدعم/التصدير، باستثناء نسخ النظام المتسلسلة ومراحل التحديث المؤقتة.
- **ملف `.env` ومفتاح `APP_KEY` غير مضمنين في النسخة الاحتياطية.** احتفظ بـ `.env` ومفتاحه في مساحة سرية منفصلة قبل أي تعديل.
- النسخ الاحتياطية تُفحص من خلال فك التشفير المؤقت، التحقق من جميع بصمات SHA-256، ثم إزالة الملفات المؤقتة. نجاح الفحص لا يثبت بعد اختبار استعادة كامل.

## عند فشل تحديث
1. اترك الموقع في Maintenance Mode ولا تحاول تشغيل Installer مرة أخرى.
2. في لوحة Super Admin اعرض سجل التحديث واسم النسخة المشفرة المرتبطة به. **لا تفترض إمكانية عكس Migrations تلقائيًا**.
3. احفظ نسخة آمنة من قاعدة البيانات الحالية الفاشلة وملفات الحادث قبل البدء بالاستعادة.
4. استخدم بيئة استرجاع **منفصلة** لها نفس إصدار PHP/DB ومفتاح `APP_KEY` الأصلي. افحص `.pqb` من `Backup Verification` قبل أي فك.
5. يُستعاد ملف `.pqb` في مساحة خاصة بواسطة مسؤول خادم مخوّل؛ راجع `database/schema.json` وملفات `database/*.jsonl` وملفات `files/`؛ تعيد `files/public/` إلى `public_html/`، وبقية `files/` إلى `puzzlequest_app/` وابق `.env` الأصلي كما هو. لا تستبدل البيانات الحية أو تخفض الجداول تلقائيًا.
6. نفّذ خطة استعادة DB بناءً على اختلاف المخطط ونوع Migration الفاشلة؛ يجوز أن تتطلب الخطة استعادة snapshot كاملة أو تصحيحًا أماميًا بدل rollback.
7. تحقق من صاحب الإدارة، الإعدادات والملفات المرفوعة، الأرصدة، Ledger، صحة DB، استئناف الطوابير وطلبات API قبل إخراج الموقع من Maintenance.

**لا يتوفر في النسخة الحالية زر استعادة تلقائية لجميع أنواع بيانات MySQL**. هذا مقصود لتجنب استرجاع غير قابل للعكس أو خسارة بيانات في تحديث فاشل، ويظل إثبات استعادة DB مشروطًا باختبار عملي على قاعدة MySQL متوافقة.
